## 特征异质性

- 特征异质性极强。输入空间包含四种截然不同的信号，尺度、稀疏性、语义密度完全不同，"一刀切"的处理方式必然丢失信息。
- 序列极长且多域。Domain D 的 P50 序列长度达 1116，max 接近 4000。四个域合计，一个用户的历史行为覆盖跨度长达 232 天。这意味着朴素的全序列 Transformer attention 在推理延迟上根本不可行。比赛明确要求通过 Latency Limit，长序列的处理方式直接决定方案的可行性边界。

## 特征工程的陷阱

EDA 揭示了三个在建模前必须解决的非平凡问题，如果跳过直接建模，后期 debug 会非常痛苦。

第一个陷阱：user_dense_feats_62~66 不是 Embedding，是统计量。
第二个陷阱：Domain D 的列顺序不统一。
第三个陷阱：domain_c_seq_47 的 item ID 量级与顶层 item_id 相同（0~278M）。

- Domain D：**有做基础处理**，baseline 里是按域单独编码的，但**没有专门的长序列策略**；只是普通进 seq_domains 流水线
- domain_c_seq_47：**有被当成普通序列特征处理**，但没有“这列很特殊”的专门分支；最多吃到通用的 seq_id_threshold / emb_skip_threshold 规则。
- user_dense_feats_62~66：**之前基本没细分处理**，只是整块 dense 一起投影；这块才是你现在 split_user_dense_tokens 真正补上的。
- 所以结论是：**不是没喂进去，而是没精细化**。
- 真正最像“收益点”的，通常就是这种“已经存在，但模型没显式建模”的部分。

- 8、81、83、84、85 存在高缺失率和大量 0 值
- 83、84、85 存在层级关系

- 某几列 Dense 特征和对应的 Int 特征之间存在 Element-Wise 的关系，如果处理方式不对，信息会在投影阶段静默丢失，不报错，但是模型永远学不到这部分信号。

## 长序列

某个域的序列长度 P50 已经过千，朴素全序列 Attention 根本过不了 Latency Check，所以长序列的处理方式在建模之前就已经被约束死了，不是一个可以自由选择的设计空间。Hierarchical Decoding 让非序列特征作为主动探针去读序列，而不是把序列压缩后被动融合。具体的压缩策略和 Query 生成方式参考了 Hyformer 的框架，但在 Multi-Domain 的场景下载做了针对性的适配。让 Query 主动去检索相关片段，即用户的行为历史，Query 是当前候选 item 和用户静态特征的联合表示。

## Baseline 已做的优化

高基数特征的 Embedding 在样本量有限的情况下，第一个 epoch 基本是在拟合噪声。工业界的处理方式是对这部分参数在特定epoch之后做重初始化，同时保留低基数特征已经积累的优化器状态。效果是让基数特征获得次”冷重启”，用更干净的初始化重新学习第二遍数据。

默认参数里，`reinit_sparse_after_epoch=1`，也就是从第 1 个 epoch 结束后就开始触发，见 `train.py (line 146)`
训练循环在每个 epoch 结束后，会调用 `model.reinit_high_cardinality_params(...)`，然后重建 Adagrad，并且只恢复没有被重置那部分参数的优化器状态，见 `trainer.py (line 319)`，真正的判断条件是 `if int(vs) > cardinality_threshold` 就重置这个 embedding，见 `model.py (line 1472)`

baseline 里这个机制虽然有，但默认配置其实比你那段话更猛。因为默认 `reinit_cardinality_threshold=0`，见 `train.py (line 151)`，而代码判断是 `vocab_size > 0` 就重置

这意味着默认不是只重置高基数特征，而是几乎所有正常的 embedding 表都会在每个 epoch 末被重置一遍，只保留少数没被重置的状态，time_embedding 还会被显式保留，见 `model.py (line 1496)`

baseline 实现不是精细版的高基数冷重启，而是一个更粗暴的全量重启近似版。另外，参数帮助文字里写着 0 表示永不重置，但这和真实代码行为是对不上的，代码实际含义不是这样。
